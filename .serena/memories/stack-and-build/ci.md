- **`platform.yaml` and `standalone.yaml` (2026-11-16, `ci/platform-workflow`, user) replaced `tests.yaml`, the four `tests-<os>.yaml` and the four `matrix-<os>.yaml`.** `platform.yaml` (`workflow_dispatch` with an `os` choice and `fail-fast`, and `workflow_call` with the same) is everything a platform owes: a `settings` job maps `os` (`linux`, `windows`, `macos-26`, `macos-27`) to the runner, browsers, time scale, `jobs`, the matrix's, plan's and standalone job's bounds — the one place those values and their reasons live — then calls `matrix.yaml` and `standalone.yaml`. Its concurrency group carries the caller's `github.workflow`, so a run by hand and the release's do not cancel each other. **Since 2026-11-19 (`ci/platform-run-name`, user) `run-name: Platform · ${{ inputs.os }}`** names a run by hand after its platform in the list of runs; GitHub ignores a called workflow's `run-name`, so CI's and the release's runs keep theirs, their job names already carrying the OS (`linux / …`, `platforms (windows) / …`). Not yet seen on a dispatched run (it needs a push). `standalone.yaml` (`workflow_call`: `runs-on`, `browsers`, `time-scale`, `timeout-minutes`) runs, in one job, the standalone tests (`test-plan.ts --mode standalone`, under `bounded.ts 900`) then conformance (`test-parallel.ts --project "conformance <browser>"` per browser, under `bounded.ts 1800`), its `.work/` as `standalone-logs-<runs-on>` on failure. **Why `--mode standalone`:** the matrix's all-pairs mode leaves the `standalone` tests out by design (spec 2026-10-12 § 3), and `tests.yaml`'s `pnpm test` was their only CI run; moving them into a matrix cell was tried and set aside by the user for a step of their own (17 tests per browser on Linux, ~20 s). Callers: `ci.yaml`'s `linux` (`os: linux`, `fail-fast: true`) and the release's `platforms` (`windows`, `macos-26`, `macos-27`). `pnpm test` (complement mode) stays the local and hook suite only. Earlier history of `tests.yaml` (2026-10-22 to 2026-11-16): it ran `pnpm build`, `pnpm test`, the conformance, per OS by hand; durations and counts: LIB-WIN-MAC, `mem:measurements/test-browsers`.
- **A timed-out test gets one retry on a slower platform, never at Linux speed (2026-11-04, `test/retry-timeouts-on-slow-runners`, user).** `tests/vitest.config.ts` sets every browser project's `retry` to `timeoutRetry(TIME_SCALE)` (`scripts/processes.ts`): `0` at `BSQ_TIME_SCALE` 1 (Linux CI, the release, local runs), `{ count: 1, condition: /^(Test|Hook) timed out in / }` above it (macOS 2, Windows 4) — a wrong result is never retried, and a file that fails to load is not a test, so not retried either. Why: a starved runner silences a worker past any bound (`mem:follow-ups/macos-ci-instability`), and the rule is no red on a library that works without fewer browsers or OS (user, 2026-11-04); at scale 1 a timeout stays red at once, as ABANDON-WEDGE did. **A test that passed on its retry is reported apart, never as a plain pass:** `Passed on retry (n tests) — it ran out of time first: look at it` with its cells after the merged report (`scripts/skip-notes.ts` `formatRetried`), a `retried` event from `scripts/progress-reporter.ts`, a `### Passed on retry (n)` section and `n retried` in the progress check run's title (`scripts/ci-progress.ts`), `RETRIED …` lines in `ci-watch.ts`. Verified 2026-11-04 with a throwaway test timing out once: retried and listed at scale 2, red at scale 1, its event marked. Not handled: a retry runs while the first attempt's leftovers may still run (Vitest cannot cancel a timed-out test). First seen on GitHub 2026-11-04: macOS 26 green 22/22 with one retry passed (MATRIX-OS, `mem:measurements/ci-runners`). **Same channels since 2026-11-05 for a test whose precondition was not reached** (`exercised`, `mem:conventions`): a `notExercised` event, `### Not exercised (n)` and `n not exercised` in the check run's title, `NOT EXERCISED …` in `ci-watch`, `Not exercised (n tests)` after the merged report, grouped by reason.
- **The live progress check run (2026-11-03, `feat/ci-live-progress`, design `docs/superpowers/specs/2026-11-03-ci-live-progress-design.md`).** A job's log cannot be read through the API until the job ends; so on CI every planner (`test-plan.ts`, hence `pnpm test` and each matrix pair; `test-parallel.ts`, hence the conformance) publishes a check run `progress · <workflow> · <BSQ_PROGRESS_LABEL or job> · <test|conformance>`, `external_id` `<run id>/<attempt>`, and prints `Live progress: <url>` in the job log. Its summary: a header, `### Failed tests (n)` (each failed test as it fails, from `scripts/progress-reporter.ts`, which every Vitest process the planners start appends to `events/<job>.ndjson`; file and hook errors too), then `### Jobs` (the `[n/N]` lines). `scripts/ci-progress.ts` is the only writer, PATCHes only when something changed, at most every 10 s (the token's 1 000 requests/hour are shared by the repository), stops with one warning on any refusal or timeout and never changes the planner's exit; its conclusion is the planner's (`success`/`failure`). **No annotations**: GitHub files such check runs under any workflow's suite of the commit (CHECK-PROGRESS, `mem:measurements/ci-runners`), so they would show on another run's page; a foreign `failure` check run does not change that run's conclusion. **Permissions:** the repository's default token is read-only and a called workflow cannot exceed its caller, so `checks: write` is granted by `matrix.yaml`'s and `standalone.yaml`'s jobs AND by every caller on the way (`platform.yaml`'s two calls, `ci.yaml` `linux`, the release's `verify` and `platforms`). **Closing step:** `Close progress`, `if: always()`, closes with `job.status` any check run the job recorded in `$RUNNER_TEMP/bsq-progress-ids` and left open (a cancel, a timeout, `fail-fast`, a planner killed by `bounded.ts`). **Following a run:** `node scripts/ci-watch.ts <run-id>` (or `--sha <sha>`) polls through `gh api` every 15 s, prints each new failure and `[n/N]` line once, then each run's conclusion; it stops 4 polls after the runs end even if a check run stayed open, and after 4 failed polls in a row (exit 2). Off CI or without a token nothing is published.

First green run on the WebdriverIO suite: PR #7, run 38182346151.

- `.github/workflows/release-and-publish.yaml` — on `v*` tags. **Since 2026-11-16 (`ci/platform-workflow`, user) the release also checks Windows, macOS 26 and macOS 27: `platforms`, a `strategy.matrix` over the three calling `platform.yaml` with `fail-fast: true` (within and across platforms), needed by `untag` and `release`.** They run nowhere before the tag, so always here, in parallel with `prior`; Linux keeps being reused from the push of `main` (no CI runs twice for a tag). Deepest nesting: release → `ci.yaml` (`verify`) → `platform.yaml` → `matrix.yaml`, 4 levels. The modules were proven on `main` on 2026-11-16 (`mem:history/2026-11-16-to-22`: Windows, macOS 26 and 27 green at once); the release's own wiring not yet. **Its duration is set by the account's 5 concurrent macOS jobs**, which both macOS runs share: ~2 h 30 measured with all three dispatched together. **Since 2026-11-03 (`ci/matrix-os`) `prior` looks for ONE run, `ci.yaml`'s push run on the tagged commit, which holds the matrix; the separate `matrix` job is gone and `verify` (calling `ci.yaml`) runs the matrix too when that run is not reusable. A tag on a commit of `main` pushed before that merge would reuse a CI run without the matrix.** What follows describes the two-run version of 2026-10-13. **Its `prior` job (2026-10-13) reuses the runs of the push of `main`**: for `ci.yaml` and `matrix.yaml` it finds the latest `push` run on the tagged commit (`gh run list --commit <sha> --event push`), waits for it (`gh run watch --exit-status`, both waits under one `timeout` deadline of 50 of the job's 60 minutes, so running out means `rerun` rather than a killed job that `untag` would answer by deleting a good tag), and outputs `success` or `rerun`; `verify` (calls `ci.yaml`) and `matrix` (calls `matrix.yaml`) run only on `rerun` — none, cancelled by a later push of `main`, failed. `consumer-smoke` always runs. `release` and `untag` need all four; `release` carries `if: ${{ !cancelled() && !failure() }}` because a skipped need would skip it. Then `pages` with `needs: release`. Pushing `main` and the tag together or apart gives the same result. Checked by hand before writing it: `gh run watch` on a completed run answers at once (0 passed, 1 failed). The wiring itself is proven only by the next release.
- **`.github/workflows/matrix.yaml` — a reusable module since 2026-11-03 (`ci/matrix-os`, design `docs/superpowers/specs/2026-11-03-matrix-os-design.md`), `workflow_call` only.** Inputs: `runs-on` (required), `browsers` (default `chrome,firefox`), `time-scale` (default `'1'`, `BSQ_TIME_SCALE` in both jobs), `timeout-minutes` (pair jobs, default 25), `plan-timeout-minutes` (default 15), `fail-fast` (default `false`; the callers that gate pass `true`). `plan` runs on the target runner with the target browsers (`--browser` each, the setup action enabling `safaridriver` when Safari is named) and outputs the pairs with a non-empty cell; `cells` runs one job per pair, `test-matrix.ts --pair <pair>` with `--engine <b> --engine isolated-<b>` per browser. **Caller since 2026-11-16: `platform.yaml` alone** (CI's Linux, the release's other platforms, a platform by hand); its pair reports are uploaded as `matrix-report-<runs-on>-<job-index>`, unique within a release run that calls it three times. Before that: `ci.yaml`'s `matrix` job and the four `matrix-<os>.yaml` by hand. The OS timeouts follow `resolveConcurrency`: the planner runs cores-less-one cells at once (2 on the macOS runners' 3 vCPU, 3 on Windows' 4; one on macOS since 2026-11-15), each bounded at 900 s × scale. First runs: MATRIX-OS, `mem:measurements/ci-runners`. Before 2026-11-03 it had its own triggers (every push of `main`, dispatch, the release's call) beside `ci.yaml`; first green on GitHub 2026-10-13 (run 38387953580, 23/23 in ~8 min).
- **A dead test fails CI in two places:** `matrix.yaml`'s `plan` (all-pairs, always fatal) and `standalone.yaml`'s standalone step (`--mode standalone`; `deadIsFatal` makes it fatal under `CI=true` with both browsers in both modes, as a complement run — the only place a dead standalone test is caught in CI since 2026-11-16, all-pairs leaving them out). Locally `pnpm test` (complement) warns, and is fatal under `CI=true` (checked 2026-10-13 with a throwaway dead test). A normal run that a dead test fails says so on its last line.
- `.github/workflows/pages.yaml` — **the site is a pure function of two tags** since 2026-09-03: `/` is the latest release tag, `/preview/` is the `preview` tag when one exists. **The ref that triggered a run is never built and never consulted**, so every trigger produces the same site and re-running anything is idempotent. Want a preview: `git tag -f preview && git push -f origin preview`. Want it gone: delete the tag.

  Triggers: `workflow_call` (from release-and-publish), push of `preview`, and `delete`. **`push` does NOT fire for a deleted ref** — `delete` is the event for that, it carries no ref filter, hence a job-level guard.

  **The bench check (2026-10-13).** Before `upload-pages-artifact`, `scripts/bench/check.ts chrome --all --dir <half>` runs from the workspace checkout on the half a run builds anew: the root (`_site`) when a release calls it (`github.ref` is its `v*` tag), `/preview/` (`_site/preview`) on a push of `preview`, nothing on `delete`. Each half is built from its own tag, page HTML included, so the root a release checked stays checked. A red page stops the deployment, not the npm publication, which comes before. **Proven on 2026-10-13** by the push of `preview` on `e5855bb`: run 38448872714, `--dir "_site/preview"` checked, then deployed, green in ~3 min.

  **The root resolves `/releases/latest` FIRST and falls back to the list, and that order is load-bearing.** `latest` is the release GitHub designates and the one npm's `latest` dist-tag follows — which is what the page's badge claims the root to be. The list alone would put the root on the newest rc once a stable version exists, while `npm i browser-sqlite` still served the stable one, and the badge would be a lie. But **every release cut so far is a PRERELEASE and `latest` excludes those**, so it answers 404 today: `gh release view` and `GET /releases/latest` both said "release not found", which is how the first preview run failed on 2026-09-03. Hence the fallback to `GET /releases?per_page=20`, newest first, drafts filtered out. The fallback stops being the live path the day a stable version ships.

  **`gh api` writes the response BODY to stdout when it fails**, and `--jq` does not filter it. So `VAR=$(gh api … || true)` captures `{"message":"Not Found",…}` as if it were data — it passed every emptiness test and died three steps later in `actions/checkout` with `fatal: invalid refspec '+refs/heads/{"message":"Not Found"…'`. **Gate on the exit status** — `if VAR=$(gh api …); then` — and shape-check anything that reaches a checkout.

  What bites, all of it silent:
  - **Order.** `assemble.ts` opens with `rmSync(target, …)`, so the root must be assembled BEFORE the preview that sits inside it. The reverse deletes the preview.
  - **The root's ASSEMBLER is copied in from the triggering checkout; only its content comes from the release tag.** Otherwise the step runs the released tag's own assembler, frozen at whatever shipped, which predates the flags and falls back to the environment — and the environment names the TRIGGER. On 2026-09-03 that made the root label itself `preview`; harmless only because the badge does not print the ref when `IS_RELEASE` is true, and a lie the moment a `delete` run sets REF_TYPE to `branch` and the real release shows "development build". The copy degrades to a no-op once a release ships a script that takes the flags.
  - **The preview step runs the preview tree's OWN assembler, and its name depends on the tag**: `assemble.mjs` before 2026-10-03, `assemble.ts` since. The step takes whichever exists; hard-coding one name fails on a preview tag from the other side of the rename.
  - **The build label is passed to `assemble.ts` as an ARGUMENT — `--ref` and `--release` — never through the environment.** Actions reposes the `GITHUB_*` variables for every step and IGNORES a step-level `env:` that tries to override them, so a run building a ref other than its trigger cannot describe itself that way. Overriding them was tried and shipped on 2026-09-03: both halves came out labelled with the triggering tag and BOTH claimed to be the published package, `/preview/` included. The preview passes no `--release`, which is the point — `preview` IS a tag, and without an explicit label the script takes any tag for a release tag.
  - **A `delete` run executes from the DEFAULT BRANCH**, so its deployment presents `refs/heads/main`. An environment restricted to tags refuses it, and a deleted tag then leaves its preview up until the next release. `main` must stay allowed for deletion to work.
  - **A run that publishes nothing could cancel one that does, and did.** `cancel-in-progress` on a shared group, `concurrency` evaluated before any job runs, and `delete` with no ref filter: deleting a merged branch on 2026-09-04 killed the preview deploy pushed two seconds earlier, then skipped itself, leaving the site on the previous build with nothing to say so. Fixed by repeating the job's guard in the group expression, so a skipping run gets `pages-noop-<run_id>` and contends with nobody. **The two conditions must stay identical; `concurrency` cannot read `env`.** The expression was verified valid on GitHub; the cancellation itself was never staged.

  **Which workflow FILE runs differs by trigger**, and it bites once: a `push` runs the file as it exists at the pushed commit, so tagging a commit that predates a change to this file fires nothing. `delete` reads the default branch; `workflow_call` runs at the caller's ref. There is no `workflow_dispatch` — removed on the user's instruction, 2026-09-03. **Re-pushing the tag UNCHANGED does nothing** — git answers `Everything up-to-date` and emits no event, so no run starts (believed otherwise until 2026-09-04). To republish without moving it: `git push origin --delete preview && git push origin preview`, which briefly takes the preview down.

  **The `github-pages` environment allows `main`, the `v*` tags and the `preview` tag** (user, 2026-09-03). `main` is there for one reason and it is not obvious: `delete` runs from the default branch, so without it a deleted `preview` tag could not take its preview down. `feat/*` was dropped — no branch deploys any more. Putting unmerged work on a real device through the `preview` tag is an exposure kept deliberately (user, 2026-08-26), which is what makes the page's "development build" banner and `buildRef()` in `scripts/bench/assemble.ts` load-bearing.
