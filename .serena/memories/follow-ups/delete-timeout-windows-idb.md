Part of `mem:follow-ups`.

- **Seen:** Windows matrix of `main` `1aa04a0a` (run 43613231041, job 132503184146), cell `firefox · IDBBatchAtomicVFS/jspi`, `close.test.ts` › "close() > waits for the worker to close the database before terminating it" — its own assertions passed; the `cleanUp` registered by `createTestClient` (`tests/browser/helpers/index.ts`) failed: `WORKER_TIMEOUT: deleting bsq-test-… did not complete within 30000 ms: the worker deleting it did not answer.` The test took 74.9 s (its file's others 0.6-25.6 s). The cleanup passed no `timeout`, so the library's default 30 s applied, which `BSQ_TIME_SCALE=4` does not stretch. Same matrix: macOS 27 lost two cells to safaridriver (`mem:follow-ups/macos-ci-instability`), unrelated.
- **Hypothesis (not verified):** `mem:follow-ups/idb-unknown-error-delete`'s mechanism — Firefox on a Windows runner holds an IndexedDB database busy while a connection closes; the next open busy-waits 10 s, fails `UnknownError`, and `createVfsInstance` retries for up to 10 s more, each attempt up to 10 s again: ~30 s at worst, which is `DEFAULT_DELETE_TIMEOUT`. The library would then give up before its own retry ends — a library inconsistency a user on a slow machine meets too, if confirmed.
