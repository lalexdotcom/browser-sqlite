## As built (2026-11-05)

- **The worker learns `debug` once, in the `open` message** (`debug?: true`); boot stages and run stages are posted only by a debug worker. No per-query flag.
- **Boot codes:** `awaiting-client`, `loading-build`, `instantiating-wasm`, `loading-vfs-module`, `creating-vfs`, `awaiting-open-lock`, `opening-database`, `awaiting-held-file`, `applying-pragmas`.
- **Run stages:** `awaiting-turn` (the worker's SQLite mutex, not the pool's queue), `preparing` (a compile; none on a cache hit), `stepping` (a statement's first `step()`, or the first after a wait — never after `computing`), `computing` (the progress handler's first call inside a step, posted before the stop test, so its presence ⇔ the step could be cut), `awaiting-credit`. Two codes for step because `db.debug` is polled: a second identical `stepping` would be invisible.
- **Durations, not timestamps:** each `run` message carries the duration of the stage it ends, on the worker's clock; the terminal reply carries the last one; the page cumulates them into `queries[].stages` (keys are the codes). No `timeOrigin` reconciliation needed. A worker dead mid-query: the page closes the current stage on its own clock.
- **`workers[i].run`** is live, cleared at the terminal reply and in `poison`.
- **The four false greens** (`abort-slot`, `early-exit`) wait for `computing` (`chunk()`) or read `stages.computing` after the next `SELECT 1` (`first()`), else `exercised`; falsified (progress handler forced to 0: red timeouts).
- **Cost:** DEBUG-RUN-STAGE-AB (`mem:measurements/routing`): no stream regression on Firefox.
- **The verdict is visible since the same branch** (`mem:follow-ups/debug-verdict-visibility`, plan `docs/superpowers/plans/2026-11-05-debug-verdict-stage.md`): a verdict with its own lease is a request `kind: 'verdict'` with `internal` queries carrying stages; a transaction's own verdict is an `internal` query of its request; a lent worker (`offer()`) leaves the transaction's request active and files the verdict in a per-slot lending list — the transaction goes on posting statements during a lend, and lends again after each one (a first design that swapped the active request misfiled them; caught by the final review). Commit `ad1ce55b` is red on Firefox one-worker pairs (fixed by `02a8417c`, history kept).
- **Left open:** a transaction's own verdict asked during a live lend is filed in the lend's request; no browser test that `run` clears on a worker's death, nor for `awaiting-turn`, multi-statement `preparing` or `drainWrites`' `stepping`.

Part of `mem:follow-ups`, opened while closing `test/retry-timeouts-on-slow-runners` (`mem:follow-ups/false-greens-remaining`).

**1. A sub-status of `RUNNING`, on the model of `boot`.** Today `db.debug.workers[i].status` is page-side (`src/pool.ts`): `READY` → `RUNNING` (set once the page has posted the query) → `ABORTING` → `READY`/`DEAD`. `RUNNING` covers everything from the post to the answer: the worker waiting for its mutex or a verdict, preparing (compiling the SQL, skipped on a cache hit), binding, stepping (`sqlite3_step()`, SQLite's VM computing the next row), handing rows over, waiting for credit between chunks. The worker reports none of it, and `debug` does not reach the worker at all. Proposed: `db.debug.workers[i].run?: RunStage`, set by worker messages as each stage begins, cleared at the end of the query — e.g. `waiting for the worker`, `preparing`, `stepping`, `waiting for credit` (the names follow item 2: codes).
- **Debug-only:** unlike `boot` (~10 messages per worker life, always sent), these are several per query and two more per paused chunk; always on, they would cost every query (the library's per-statement cost was measured to 0.05 ms, ROUTING-VS-MAIN, FAST-STEP). The page passes a flag with each query of a `debug` client; production pays one boolean test per transition and per progress-handler call.
- **`stepping` from the progress handler's first call** (every `PROGRESS_OPS` = 100 000 VM instructions, `src/worker/worker.ts`), not around each `sqlite3_step()` (called once per row: one message per row is too much even in debug). It means "in a long computation"; a short statement goes from `preparing` to its end without it. The handler exists on `async`/`jspi`, and on `sync` only with the shared abort slot (cross-origin isolated).
- **Size:** ~80-120 lines + tests: a public `RunStage` type exported as `BootStage` is, the worker's announcements at transitions it already passes, the page's record and reset, a test helper `theQueryIsStepping`, a CHANGELOG `Added` entry.
- **Uses:** the tests' last known false greens (`abort-slot`, `early-exit`: wait for `stepping` before a `break`, check it after a `first()`, `mem:follow-ups/false-greens-remaining`); and diagnosis — where a statement sat on a starved runner (mutex, prepare, step), what `tx-timeout`'s unexplained Windows red and the silent Chrome workers lacked.
- A cheaper variant was considered: a one-shot `steppedAt` timestamp on the query record. Enough for the two tests, no diagnosis; the user chose the sub-status.

**2. `BootStage` as codes, not descriptive text (user, 2026-11-05).** `BootStage` (`src/types/protocol.ts`, public through `src/debug.ts` and `src/index.ts`) is today a union of English phrases (`'waiting for the client'`, `'loading the build'`, `'instantiating wasm'`, `'loading the VFS module'`, `'creating the VFS'`, `'waiting for the open lock'`, `'opening the database'`, `'waiting for a held file'`, `'applying pragmas'`) — used as values by tests (`lifecycle`, `open-retry`, `startup-probe`), in messages, and in the STARTUP-PROBE-MAC measurements. They become codes (e.g. `'client-wait'`, `'build-load'`…; exact spelling to decide), the text left to wherever a message is built. A breaking change of a public type: `CHANGELOG` `Breaking`, `API.md`'s `debug` section, every test and helper that compares a stage. `RunStage` (item 1) is born as codes.
