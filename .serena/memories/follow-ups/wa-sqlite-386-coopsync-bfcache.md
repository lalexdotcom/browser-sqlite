## Why no library test (2026-11-02)

**#386 does fix #362**, measured that day on wa-sqlite alone (the `bf.html` probe: a module worker opens `OPFSCoopSyncVFS`, keeps the database open, the page navigates to itself): without #386 the next page's `create()` fails every other page (`removeEntry` → `NoModificationAllowedError`), with it 10 of 10 — in the user's Chrome 156 (macOS), in the suite's Chrome for Testing 153 under WebdriverIO (`.work` throwaway script reusing `resolveBrowsers`/`browserCapabilities`), and in a `noopener` popup alike. A delay of up to 1 s before `create()` changes nothing: the cached page holds its temporary files for as long as it is cached.

**The library does not reach #362 in the same navigation, with or without #386**, so a library test could not protect #386. A throwaway Vitest spike (`spike/bfcache-386`, deleted, never committed) opened a top-level page with `window.open(url, '_blank', 'noopener')` from the test, the page opened the library's client on `OPFSCoopSyncVFS/sync`, kept it open and navigated to a second page; `pagehide.persisted === true`; the second page recorded its workers' boot stages (no `waiting for a held file`, i.e. no `createVfsInstance` retry) and `navigator.locks.query()` before opening. With #386 removed from the installed VFS (mutant restored by `trap`, checked with `cmp` against `c4f832ea`): the cached page still HELD its locks (its `.ahp-*` directory, `ahp:/<file>`, the library's `bsq:client:` marker), so the sweep skipped its directory and the open went through in 54-60 ms. Why Chrome keeps a cached library page's locks where it releases wa-sqlite-alone's is not known (a Chrome bfcache internal; not pursued, user). September's LEAK-LIB (Playwright, library: ~85 ms retry) is not reproduced in this harness.

**Traps found on the way**, kept for the next navigation test (`mem:follow-ups/bfcache-auto-suspend`): a page whose `BroadcastChannel` receives a message while cached is evicted by Chrome — the spike's first version kept a reporting channel open on every page, the second page's reports evicted the first, and the library seemed to "escape" #362 (the same effect turned wa-sqlite alone's failures into 8 of 8 successes). A page in the cache must have no channel open: open one to post, close it, and listen only on the last page. And a mutant left in `node_modules` (`mem:lessons/process`).

**The harness that works** (Chrome, WebDriver): the test opens `window.open(url, '_blank', 'noopener')` (no popup blocking under chromedriver), the page imports `browser-sqlite/built` through Vite, reports on a short-lived `BroadcastChannel`, proves the cache with `pagehide.persisted`, and the last page closes its client and `window.close()`s on the test's request; the storage wipe after the file passed.
