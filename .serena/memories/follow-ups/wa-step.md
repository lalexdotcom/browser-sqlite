# Follow-up — wa-sqlite's async `step()` wrapper costs every read, most on Firefox

Part of `mem:follow-ups`, moved here on 2026-10-08 to keep that file under 40 000 characters. **A dedicated workstream for a new session, possibly opened as an upstream Discussion (user, 2026-10-08).**

**Scope set by the user (2026-10-08):** a workstream of its own, started in a new session; it may begin as a discussion on wa-sqlite's forum (GitHub Discussions). It applies to every engine — Chromium and WebKit gain too, Firefox the most. Prototype and measure on `MemoryVFS`, check the other VFS once a solution exists. Upstream is not preferred: a solution that avoids changing wa-sqlite is better, unless upstream is the only or the best-performing one (`mem:conventions`).

**What each solution asks of the library:**
- **Library-side fast step** (fastest, measured below): the worker's two `sqlite.step(stmt)` call sites (the row loop in `query`'s `run()`, and the control-statement loop) go through a step that reproduces `retry()`/`check()`; a start-up guard checks `Module.retryOps`/`pendingOps` and falls back to `sqlite.step` if their shape changed. No public API change, for us or for wa-sqlite.
- **Upstream, API unchanged** (`step()` stays `async`, no nested `retry()`): nothing to change in the library — the gain arrives at the repin — but about half of it on `jspi`, ~80-85 % on `sync`/`async` (Firefox).
- **Upstream, `step()` returning `number | Promise<number>`**: breaking for wa-sqlite users (`.then` on a number; its type is `step(stmt: number): Promise<number>`, `src/types/index.d.ts:765`). The library's `await sqlite.step()` keeps working unchanged (awaiting a number costs ~5 ns on a stock Firefox); skipping the `await` when a number comes back is an optional one-line refinement. The local typing of the façade would follow the new type.
- **Upstream, a new synchronous-when-possible method beside `step()`**: additive for wa-sqlite; the library switches its call sites to it — a small change, no internals reproduced.

**For an upstream discussion, what is already reproducible with wa-sqlite alone** (`mem:conventions`: upstream evidence must stand without this library): the probe is a module worker that imports a build's glue, `sqlite-api.js` and `MemoryVFS`, fills a table of 4 000 000 `(a, b)` integer rows, and times `while ((await sqlite3.step(s)) === SQLITE_ROW)` against the raw export and the fast step; to be rewritten as a runnable snippet or test in wa-sqlite's tree before posting. **Time Firefox on a stock build** — Playwright's Firefox inflates every `await` (FF-PW-AWAIT, `mem:measurements/footprint`), which matters for upstream's own CI if it moves to Playwright (Discussion #373).

**The invariant any fast step must keep: never decide ahead that a call is synchronous — look at what it returned.** Assuming it would break each build differently: `sync` — a VFS cannot suspend there, but `OPFSCoopSyncVFS` answers `SQLITE_BUSY` and queues `Module.retryOps`; ignoring them surfaces a false "database is locked". `async` — calling the raw export while the VFS unwinds returns a meaningless value with the operation still in flight, and calling into the module again corrupts Asyncify's state; hence `ccall` without `async`, which detects the unwind (`Asyncify.currData` changed) and returns `whenDone()`'s promise. `jspi` — the export always returns a promise; comparing it to `SQLITE_ROW` ends the loop at the first row, a silent truncation. So: a number and nothing pending → synchronous; a promise, or any retry/pending operation before or after the call → wa-sqlite's full asynchronous path.

## The findings so far (2026-10-08)

**Mostly a test-browser artefact, and what is left is real.** Measured on 4 000 000 rows of two integers, `MemoryVFS` (the user's ruling: prototype and measure on `MemoryVFS`, check the other VFS once a fix exists), direct harness. With Playwright's `firefox-1538` the library's `chunk()` took 22.5 s `sync` / 26 `async` / 34 `jspi` against Chromium 1.3 / 1.6 / 2.4 — but that binary is 10-30× slower on `await` (FF-PW-AWAIT, `mem:measurements/footprint`). **On a stock Firefox 157: `chunk()` 3.4 s `sync`, 4.4 `async`, 5.3 `jspi`; `stream()` 4.2 s `sync`** — 2.2-2.6× Chromium. The same before the binary protocol (`f796fb8`, Playwright's binary: 22.9 / 35.3 s).

**Where it goes — wa-sqlite alone in a worker, `sync` build, stock Firefox / Chromium, ms:** raw `_sqlite3_step` 163 / 207; raw step + reading both columns 240 / 310; `await sqlite3.step()` **2 829** / 877; `sqlite3.step()` + `sqlite3.row()` 3 276 / 1 302; wa-sqlite's `retry()` around the raw call 1 764 / 548; `cwrap` with `{ async: true }` awaited 330 / 565. So on a real Firefox the per-row cost is the façade's `step()` — an `async` function awaiting the `async` `retry()`, ~0.65 µs a row against ~0.17 on Chromium — not SQLite, not `RowWriter`, not the transport. The Firefox `jspi` extra is on top. The page half of `stream()` (one `next()` per row) is the same kind of cost.

**The fast step, studied on wa-sqlite alone (no library), 4 000 000 rows, 2 passes, stock Firefox / Chromium:** a `fastStep` that calls the export directly and stays synchronous unless the call returns a promise or `Module.retryOps`/`pendingOps` is non-empty, replicating `retry()` (wait retryOps, at most one re-call when `rc !== OK` and retryOps were queued, wait pendingOps, `e.code` on their failure) and `check()` (`ROW`/`DONE`, else `SQLiteError` with `sqlite3_errmsg`). The call per build, read from the glue: `sync` the raw export (`ccall` there is always synchronous); `async` **`ccall` without the `async` option**, which returns the number when nothing unwound and `Asyncify.whenDone()`'s promise when the VFS suspended; `jspi` the `promising` export, always a promise. `step()` → `fastStep`, ms: `sync`/`MemoryVFS` 2 835 → **216** / 893 → **213**; `async`/`MemoryVFS` 3 282 → **707** / 970 → **460**; `jspi`/`MemoryVFS` 4 409 → **2 400** / 1 641 → **1 118**; `async`/`MemoryAsyncVFS` with `cache_size = 10` (15 846 calls a pass really suspended, the rest returned a number) 3 449 → **807** / 1 001 → **520**; `jspi`/`MemoryAsyncVFS` 4 545 → **2 502** / 1 603 → **1 070**. Row counts exact everywhere. Not yet tried in the library.

**Upstream-compatible variant** (`step()` kept `async`, no nested `retry()`), same probe, ms, stock Firefox / Chromium: `sync` 450 / 310 (lib fast step 214 / 210), `async` 968 / 626 (730 / 486), `jspi` 3 324-3 486 / 1 253-1 311 (2 456-2 864 / 1 075) — most of the gain on `sync`/`async`, about half on `jspi`; the lib-side step stays ~2× faster.

**WebKit** (Playwright's Linux WebKit 26.6, webkit-2370 — not Safari): `await` costs about what Chromium's does (4 000 000 awaited `async` calls with an inner `await`: 163 ms against 205); `step()` → upstream variant → lib fast step: `sync` 688-714 → 270-281 → 157-169, `jspi` 1 049-1 059 → 670-684 → 548-556; `async` unreadable — every pass after the first runs 3.6-4.1 s whatever the step, the Asyncify-on-WebKit slowdown already seen on Safari (IDB-SIGNAL). Real Safari not measured: it takes the user's Mac, the probe served from the container.

**Chromium in the library — an estimate, not measured:** the wrapper is ~0.5-0.7 s of `chunk()`'s 1.3 / 1.6 / 2.4 s on 4 000 000 narrow rows, so roughly −50 % `sync`, −30 % `async`, −20-25 % `jspi` on such reads, and ~10-15 % on a 10 000-row `read()`; nothing on one-row queries.

**wa-sqlite's `MemoryAsyncVFS.create()` returns a `MemoryVFS`** (`new MemoryVFS(name, module)`), so anything created through it never suspends — a one-line upstream report, not sent.
