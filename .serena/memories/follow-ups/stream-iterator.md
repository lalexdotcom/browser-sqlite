# Follow-up — `stream()` through a hand-written iterator instead of three nested async generators

Part of `mem:follow-ups`, opened 2026-10-16 (user). **Its own branch, after `perf/fast-step`.**

**Why.** After the fast step, `stream()`'s cost is page side: `streamRows` (`src/queries.ts`) → `streamWithRetry` (`yield*`) → `stream` (`yield*`, `src/client.ts`), one `next()` per row through three async generators. Pure-JS probe (STREAM-GEN, `mem:measurements/footprint`), 4 000 000 rows, ms, Chrome 153 / Firefox 155.0.1: three nested generators 802 / 4 489, one generator 365 / 2 190, hand-written iterator 122 / 185, chunks read by a plain `for` 15 / 21. Not yet tried in the library.

**The design discussed with the user (2026-10-16) — how the risk is kept small:**
1. **The lifecycle stays in the generators, at chunk granularity.** `chunk`, `streamWithRetry` and `stream`'s deadline keep running as generators but yield chunks, not rows; their `finally` keep the abandon on `break`, the deadline release and the retry (before the first row = before the first chunk). On top, a small adapter `flatten(chunks)` serves the current chunk's rows with `next()` returning `Promise.resolve(...)`, and its `return()`/`throw()` delegate to the chunk generator. That is the probe's iterator arm. The hand-written part has four known traps: two `next()` not awaited must not fetch two chunks (serialise on the pending promise); a `return()` during an in-flight `next()` waits for it before closing the source; an error from the source ends the iterator; `next()` after `done` stays `done` without calling the source.
2. **The adapter tested alone, in the unit project**, on a scripted source: one test per trap, plus `break` mid-chunk (exactly one `return()` on the source), `throw()`, a rejection after N rows. Better still, a **differential test**: the same scripted consumer actions (read k rows, `break`, `throw`, source error at chunk j) against today's three-generator shape and against the adapter, traces required identical (rows received, `return()` calls on the source, errors) — today's behaviour is the reference.
3. **The browser tests that already pin `stream()`'s semantics run unchanged**: `abandon`, `early-exit`, `stream-retention`, `query-timeout`, `interrupt`, `queries`, `results`, `routing`, `writer-spread`, and the transaction tests' `tx.stream()`. A test that has to change means the semantics changed.
4. **The public type stays `AsyncGenerator`** (inferred from `async function*` today): the adapter implements `next`, `return`, `throw` and `[Symbol.asyncIterator]`.

Measure it in the library as FAST-STEP was (direct harness, stock browsers with the update policy, `main` against the branch interleaved, row counts checked).
