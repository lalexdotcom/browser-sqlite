**Measured from the job logs (2026-10-26): on macOS, timers are slow in Chrome and Firefox, not in Safari.** The failing test (1001 rows, a `setTimeout(0)` per row) takes 4.3-4.5 s on Linux in all four cells (Chrome and Firefox), but 20-23 s on macOS 26 and 27 in every Chrome and Firefox cell — 22.3, 22.5, 22.7 s, nearly constant across cells, which points at a deterministic timer delay rather than CPU contention — and 8.1-8.2 s in Safari cells. The run that failed only crossed 30 s (32.1 s) on top of that baseline. Per-file times of the big Chrome cell also vary run to run on macOS 26 (`results.test.ts` 2.8 → 24.6 s, `inspect-marker.test.ts` 7.4 → 37.2 s): load comes on top.

**Hypothesis to test (not verified):** macOS throttles timers of apps that are not frontmost (App Nap, timer coalescing); safaridriver keeps Safari in front, while the Chrome and Firefox windows WebDriver opens beside it are not. Candidate remedies, each to measure: `defaults write NSGlobalDomain NSAppSleepDisabled -bool YES` (App Nap off) in the macOS workflows; Chrome's `--disable-background-timer-throttling --disable-renderer-backgrounding --disable-backgrounding-occluded-windows`; Firefox's background-timer prefs; or `BSQ_TIME_SCALE` > 1 on macOS as Windows has (masks rather than fixes). First step: a probe of `setTimeout(0)` latency per browser on the macOS runner, with and without App Nap disabled.

**TIMER-PROBE, 2026-10-26, GitHub `macos-26`, run 40357075889 (`spike/macos-timers`, `tests/browser/pairs/spike-timers.test.ts`):** p50 latency of 500 × `setTimeout(0)`, 3 rounds per cell, two cells per browser. Headless Chrome: page 16-24.5 ms, worker 16.5-23.5 ms; headless Firefox: page 15-21 ms, worker 17-24 ms; Safari (windowed): page 8 ms, worker 5 ms; headless Chrome on Linux (this container): 6 ms both. `setTimeout(10)`: Chrome/Firefox 22-69 ms, Safari 12 ms, Linux 11.5 ms. **App Nap is refuted:** with `defaults write NSGlobalDomain NSAppSleepDisabled -bool YES` the numbers are the same (Chrome 16.6-27 ms, Firefox 19-23 ms). Chrome's p50 sits at 16.6 ms, one 60 Hz frame — timers aligned to a frame rhythm, unverified. **Headless is refuted too (run 40359426948, 2026-10-26):** windowed Chrome (`BSQ_SPIKE_HEADED=1`; its user agent has no "Headless") page 16-25.6 ms, worker 17-25.6 ms, against headless Chrome 14.5-24 ms and 16.6-26 ms in the same run; Firefox 18-22 ms either way (its user agent does not say headless, so the extractor's label is meaningless for it); Safari 8 ms / 5-6 ms. Every page reported `visibility: visible`, `hasFocus: false`, Safari's too. The Chrome-switches arm never ran: safaridriver refused the planner's Safari probe (below). **Left:** what Chrome and Firefox share and Safari does not is how they are started — children of chromedriver/geckodriver, themselves children of the job, while safaridriver has the system launch Safari; unverified guess: they inherit a background task policy and macOS coalesces their timers. **The question that decides the next step:** does a real Mac show it (then the library pays ~16 ms per `setTimeout(0)` on macOS Chrome and Firefox, a library subject), or only the runner (then `BSQ_TIME_SCALE=2` on the macOS workflows, as Windows has 4)? **Answered 2026-10-26 (TIMER-PROBE-MAC): the runner, not macOS.** The same measurement as a page served from the container (`scripts/static-server.ts`, port 8099 forwarded by VS Code; the user's Mac has no Node, by design — never ask to run Node there), opened by hand in a foreground tab on the user's Mac: Chrome 155 page 4.5 ms, worker 5 ms, `setTimeout(10)` 11 ms; Firefox 158 5 / 5 / 11-12 ms; Safari 27.0.1 8 / 5 / 12 ms (identical to the runner's Safari). So a user's Chrome or Firefox on macOS does not pay it; the slowdown belongs to the `macos-26` runner or to browsers started by chromedriver/geckodriver there. **Decided by the user (2026-10-26):** `tests-macos-26.yaml` and `tests-macos-27.yaml` pass `time-scale: '2'` and `timeout-minutes: 150` (`ci/macos-time-scale`); the exact runner cause stays open at low priority (untested: a task policy inherited from chromedriver/geckodriver, Chrome's anti-throttling switches); the spike branch `spike/macos-timers`, its probe, its workflow and its `BSQ_SPIKE_*` switches are deleted, its GitHub runs too (user). The TIMER-PROBE runs above (40357075889, 40359426948) are therefore no longer readable; their numbers are the ones written here.
