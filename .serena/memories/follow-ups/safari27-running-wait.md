# Follow-up — on Safari 27, a long statement of the routing tests is never seen running

**Status: DONE (2026-10-28, `fix/safari27-wait-yield`)** — found the same day on the first macOS 27 runs after `feat/sqlite-routing`'s merge; a test fault, not a library one: `waitUntil` polled on a timer Safari 27 held to 1 Hz. Fixed in the helper, macOS 27 green twice (§ Fix).

Part of `mem:follow-ups`.

**What fails.** `tests-macos-27.yaml` on `main` `7cb5122`, twice (runs 40712191843 and 40719361310): tests added by the routing branch that wait with `waitUntil(theQueryIsRunning(db, sql))` (`tests/browser/helpers/index.ts`: a request without `endTime` whose worker's debug status is `RUNNING` and whose last query has the statement's text) time out at 10 s (5 s × `BSQ_TIME_SCALE=2`) on Safari 27, on `OPFSWriteAheadVFS/sync` and `OPFSAdaptiveVFS/jspi`. Run 1: `tx-stream` "a savepointed tx.stream() write aborted before affected is undone…" on both pairs, `stream-write` "an abort while the worker steps the write rolls it back" (Adaptive), `verdict` "waits for a query stepping on the worker" (Adaptive). Run 2: the `tx-stream` test on both pairs, the `verdict` test on WriteAhead. The rest of the suite passes on Safari 27 (559 of 562 files).

**What does not fail.** The same tests pass on Safari 26.6.2 (`tests-macos-26.yaml`, run 40712185970), in 0.4-3 s, so the statement is seen running there; older tests using the same helper with longer statements (`interrupt.test.ts`, 20-40 M iterations) pass on Safari 27. macOS 27 was green before the branch (push of `a17b6c6`, 2026-10-26). Chrome and Firefox on every OS green, the matrix 23/23.

**Not known yet:** whether on Safari 27 the statement never starts (a verdict or a lease waiting), or runs without `db.debug` showing it `RUNNING`, or ends before it is polled. A first guess — the failing tests' statements are short (1-2 M iterations) and Safari finishes them unseen — is weakened by Safari 26 seeing them at once.

**Alone, it does not reproduce (spike run 40725890211, 2026-10-28).** One spike file, one Vitest process per project: on Safari 27.0.1, `OPFSWriteAheadVFS/sync` and `OPFSAdaptiveVFS/jspi` — the failing pairs — see a cold 2 M-step `all()`, the same warm, and a savepointed `tx.stream()` write running in 11-14 ms, a 20 M-step read in ~100 ms; Safari 26.6.2 alike. So the verdict, the read, the streamed write and `db.debug`'s view all work there: **the failure needs the suite's context** (earlier files or tests of the cell). Aside: on the `async` build (Safari 26 and 27), the third client of that file (a cold 20 M-step read) got its request only 4-9 s after the call — something earlier in the file held it; not investigated.

**In its cell, it reproduces, and the poll is what is late (spike run 40727661900, 2026-10-28).** The two cells whole through the planner, Safari 27 alone: `OPFSWriteAheadVFS/sync` red on `verdict` "waits for a query stepping on the worker" only (its `tx-stream` case green this time), `OPFSAdaptiveVFS/jspi` green — intermittent even in the cell. The debug history of the timed-out wait: at +1 ms no read yet; the read gets its worker at once (`acq=1`, no queue, no request or worker state left by earlier tests) and ends at +365 ms; **the next poll is at +760 ms**, by when it is over. The poll loop is `await sleep(0)` (`setTimeout(0)`) and would have seen the read at any turn in 2-364 ms. `db.debug` is live main-thread state (`src/debug.ts`): `query.endTime`/`request.endTime` are set by `Date.now()` when the main thread handles the worker's message, so the main thread handled a message at +365 while the timer did not fire before +760. **So the library runs the statement; the test's observation misses it** — leaning to a late timer over a busy main thread, not settled. Worker status `READY/applying pragmas` in every sample, which proves nothing: no sample fell while it ran.

**Cause found: Safari 27 runs the test page's timers once a second, its main thread idle (run 40732354209, 2026-10-28).** Probe in `waitUntil`: each `setTimeout(0)` timed, and a worker posting `Date.now()` every 100 ms (a message handled late would mean a busy main thread). `OPFSAdaptiveVFS/jspi` red on all three tests (`stream-write` "the DELETE running", `tx-stream` "the INSERT running", `verdict` "the long read to run"), `OPFSWriteAheadVFS/sync` green this time. In each: **`setTimeout(0)` fired after ~1000 ms every time** (`+1:837 +838:1002 +1841:997 …`, 21 sleeps in 10 s; the first one 438-837 ms), while **the worker's messages arrived 1-25 ms late at most** — the main thread was free, only timers were held back. `document.visibilityState = visible`, `hasFocus() = false`. The watched statements run 220-650 ms (the 2 M-step read 361-364 ms, a DELETE 645 ms, an INSERT 221 ms), so they start and end between two polls. Why only the routing branch's tests: the older users of `theQueryIsRunning` (`interrupt.test.ts`, 20-40 M iterations) run several seconds, longer than a timer period. Why intermittent, and which pair: not known — the throttle lands on some cells' pages and not others (WriteAhead red in 40727661900, Adaptive here). Safari 26 does not throttle (the same tests seen running in 0.4-3 s). **Not a library fault in what was observed**, but any library timer (`setTimeout` deadlines, back-off) would be held back the same way in such a page.

**Probe note:** its worker is built with the helper's `NativeWorker`; through `globalThis.Worker` an `interceptWorkers()` test records it as `records[0]` (`abort-slot` went red in the pre-push). Run 40732354209 was dispatched through `tests-macos-27.yaml`/`tests.yaml` edited on the spike branch — the method the user rejected the same day (`mem:lessons/process`). The spike branch and its four runs were deleted on 2026-10-28, the diagnosis recorded (SAFARI27-TIMER-1HZ, `mem:measurements/ci-runners`).

**Fix (2026-10-28, `fix/safari27-wait-yield`, user: "on résout le problème").** `waitUntil` (`tests/browser/helpers/index.ts`) yields between checks with `nextTask()` — one reused `MessageChannel`, a FIFO of resolvers, a `postMessage` per turn — instead of `sleep(0)`; a message task is not held back by the throttle. The library is unchanged. Verified: `pnpm test` local 394/394 (Chrome/Firefox, cell times unchanged); `tests-macos-27.yaml` on the branch, runs 40741792029 and 40745756595: 562/562 files and conformance 9/9 each, the two cells that failed (`[2/28]` WriteAhead/sync, `[3/28]` Adaptive/jspi, the same place in the order as in the red runs) green.

**Left open, not tracked elsewhere:** why Safari 27 throttles — a rule of Safari 27 itself (a page or a window left without focus or interaction; it appears only after a while in a cell, never in a one-file spike) or an effect of the safaridriver session — is not known; Vitest's test iframe is visible and viewport-sized (its orchestrator, checked). Cheapest test: a page measuring `setTimeout(0)` continuously in Safari 27 on a Mac, visible without focus behind another window, no WebDriver. If it is Safari itself, the library's own timers would be held the same way in such a page: `close()`'s `setTimeout(0)` (`src/client.ts`) and `deleteDatabase`'s (`src/delete.ts`) up to 1 s each, every deadline and back-off timer late by up to 1 s.
