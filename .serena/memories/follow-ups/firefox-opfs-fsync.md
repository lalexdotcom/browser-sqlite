# Follow-up — Firefox + OPFS: every file create/open/close/delete costs fsyncs — what the library can avoid (user, 2026-10-14)

**Status: OPEN** — counted on 2026-10-29 (JOURNAL-PROBE): `OPFSAdaptiveVFS` without `readwrite-unsafe` pays the bug's cycle at every commit, the other VFS do not; on Windows Firefox that is 150-164 ms per commit against 9 ms without a journal file. The fix (upstream) and the 30 s default open timeout on Windows Firefox await.

Part of `mem:follow-ups`; moved out of it on 2026-10-26.

Firefox keeps a per-origin SQLite metadata database for OPFS (`storage/default/<origin>/fs/metadata.sqlite`, in the profile) in rollback-journal mode: one create + `createSyncAccessHandle` + `close` + `removeEntry` cycle runs 7 transactions, 21 fsyncs (Chrome: 0). Reported upstream as [Mozilla bug 2072928](https://bugzilla.mozilla.org/show_bug.cgi?id=2072928) (third party, 2026-09-17, UNCONFIRMED, unassigned, no Mozilla reply; `PRAGMA journal_mode = WAL` in Firefox's `GetStorageConnection` takes a cycle from 75 to 1.9 ms on Linux) — no Windows numbers there. Data reads/writes are unaffected; the cost is per metadata operation and scales with the cost of an fsync: Linux 79 ms/cycle in that report, macOS ~4× Chrome (its `fsync` does not flush the drive). Not reachable from a page: the fix is Mozilla's.

**Measured on Windows (2026-10-14, OPFS-PROBE, `mem:measurements/held-handles`):** Firefox pays 40-220 ms per OPFS file operation on `windows-latest` (Chrome 0.5-2 ms, Firefox on Linux and macOS 1-7 ms); Firefox OPFS tests run 7-16× slower than Chrome there.

**What each VFS pays, counted (2026-10-29, JOURNAL-PROBE, `mem:measurements/held-handles`, Firefox 155 and Chrome 153 on Linux):** per autocommit write, `OPFSAdaptiveVFS` without `readwrite-unsafe` (Firefox, Safari) runs `getFileHandle(create)` + `createSyncAccessHandle` + `close` + `removeEntry` on its `-journal` — the bug's cycle — plus two `getFileHandle` lookups (`-journal`, `-wal`); it keeps the database's handle between commits, not the journal's. `OPFSCoopSyncVFS` keeps `-journal` open and truncates it instead of removing it, so it pays nothing per commit — its cost is per hand-over between clients (`close` and `createSyncAccessHandle` of each file it holds). `OPFSWriteAheadVFS` and `AccessHandlePoolVFS` make no metadata call per commit. **`journal_mode = PERSIST`/`TRUNCATE` is no lever:** `OPFSAdaptiveVFS` refuses both without `readwrite-unsafe` (`disk I/O error`, the mode stays `delete`) — likely because SQLite keeps a persisted journal open between transactions, an exclusive handle other connections would need (read, not measured) — and on Chrome, where it accepts them, they cost two `createSyncAccessHandle` + `close` per commit. `journal_mode = MEMORY` removes the cycle but loses crash safety: not a default (`defaultPragmas`'s bar). What remains: an upstream change in which `OPFSAdaptiveVFS` keeps the `-journal` handle with the database's and hands both over together, truncating instead of removing, as `OPFSCoopSyncVFS` does; `temp_store = MEMORY` (`mem:follow-ups/temp-store-anycontext`) is unrelated to this cycle.

**Autocommit writes on Windows Firefox (2026-10-29, `tests-windows.yaml` runs 40712181489 and 40910548488):** `results.test.ts` › "decodes short, long and invalid texts as before" — ~140 single-row `INSERT`s, one commit each — took 88 s on `firefox · OPFSAdaptiveVFS/jspi` on 2026-10-28 and timed out at 120 s on 2026-10-29, against 8 s on Chrome in the same run. A `-journal` created and removed per write transaction, paying the metadata fsyncs above — **confirmed by count** on 2026-10-29 (the paragraph above), and **timed on `windows-latest` the same day** (run 40968323465, JOURNAL-PROBE): Firefox `OPFSAdaptiveVFS` 150-164 ms per autocommit write in `delete` against 9 ms in `memory`, Chrome 22.7 ms; the ~630 ms per commit of the test ran under the suite's parallel jobs. The test now inserts in one transaction (its subject is decoding), and on Windows (run 40923529480) its slowest cell fell to 3.1 s (others 0.3-1.4 s): the same rows in one commit instead of ~140 — **the per-commit cost dominates there.** So every autocommit write costs a Windows Firefox user of `OPFSAdaptiveVFS` 150 ms or more, ~95 % of it the journal's cycle; `OPFSWriteAheadVFS` commits in 2 ms there.

**The library's default open timeout (30 s, `src/client.ts`) can be too short on Firefox on Windows (2026-10-15, run 38721500216):** a single `OPFSWriteAheadVFS` client (`bulk-write` › "writes nothing when the abort beats the first batch") got `TIMEOUT: Worker 1 did not become ready within 30000 ms. No client of this library holds it` under the suite's 3 parallel jobs. A user with several tabs, or a loaded machine, could meet it. To decide (user-visible): an adaptive default, a larger one, or a note in `VFS.md`. Meanwhile the tests stretch the default by BSQ_TIME_SCALE (`tests/browser/helpers/library.ts`, the `browser-sqlite` alias of the browser tests; the build itself unchanged at factor 1).

**Two CoopSync clients on Windows Firefox, with wa-sqlite #381 carried (2026-10-16, COOPSYNC-381-WINDOWS, `mem:measurements/held-handles`):** under the tests' 120 s open timeout, 54 two-client attempts of `coopsync-handover` failed no statement, where before #381 the first test met 12 × the 30 s open `TIMEOUT` and 2 raw errors in 20 attempts. An attempt takes 25-60 s there (~150 ms on Linux), so the file runs 3 attempts on Firefox on Windows instead of 20; its skip there was removed on 2026-10-16. Unmeasured: whether the library's 30 s default lets a second client open there — the paragraph above. A user with two tabs on Windows Firefox pays that hand-over cost; the library paying less per hand-over is the path the user wants to explore, or a Firefox that fixes bug 2072928 (it counts once `scripts/browsers.ts` pins it). A changed default is consumer-visible. Also possible: a note in `VFS.md` on Firefox + OPFS. Open, the user's: whether to add our Windows numbers to bug 2072928.
