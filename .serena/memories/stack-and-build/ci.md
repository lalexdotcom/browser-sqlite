# CI — the GitHub workflows

Part of `mem:stack-and-build`, moved out of its § CI and hooks on 2026-10-13 when that memory passed 40 000 characters. The local hooks are in `mem:git-hooks`; what runs where, and when, in `mem:conventions` (§ What runs where).

- **`.github/actions/setup` (composite, 2026-10-14, `ci/windows-macos`) — the one setup procedure of every job that drives a browser** (`matrix.yaml` `plan`/`cells`, the release's `consumer-smoke`, `pages.yaml`'s bench check, `tests.yaml`; `ci.yaml`'s `checks` uses it with `browsers: ''`). Inputs: `browsers` (comma-separated, default `chrome,firefox`, empty for none; the release and `pages.yaml` pass `chrome`) and `node-setup` (default `'true'`; `pages.yaml` passes `'false'`, it sets up Node itself for its tag checkouts). Steps: pnpm, Node 24, `pnpm install --frozen-lockfile`; `sudo safaridriver --enable` when the list names `safari` on macOS (2026-10-22; off macOS the install then fails with Safari's macOS-only error); the WebdriverIO cache keyed `wdio-<os>-<arch>-<browsers with - for ,>-<hash of scripts/browsers.ts>` (a cache key cannot hold a comma — the first Windows/macOS runs died on it); AppArmor only `if: runner.os == 'Linux'`; `node scripts/browsers.ts install "<browsers>"`. Every `run:` has `shell: bash`. Proven on Windows and macOS (Task 6 of the plan) and on Linux before the merge (2026-10-15, PR #9 of this repo): `ci.yaml` run 38745729071 green (Type check included — the final review had caught a shim importing the untracked `tests/build/`), `matrix.yaml` dispatched on the branch, run 38745725725, 23/23. Still to see: `pages.yaml` at the next push of `preview`, `consumer-smoke` at the next release.
- **`tests.yaml` (`workflow_call`: `runs-on`, `time-scale` default `'1'`, `timeout-minutes` default 90, `browsers` default `chrome,firefox` — passed to the setup action, as `--browser` to `pnpm test` and as one `--project "conformance <browser>"` each to `test-parallel.ts` under `test:conformance`'s 1800 s, since that script's `"conformance *"` would add to a glob rather than narrow it; 2026-10-22, `ci/linux-via-tests`) and its callers `ci.yaml`'s `linux` job (`ubuntu-latest`), `tests-ubuntu.yaml` ("Tests (Ubuntu)", `ubuntu-latest`, by hand), `tests-windows.yaml` (`windows-latest`, time-scale `'4'`, 240 min) , `tests-macos-26.yaml` ("Tests (macOS 26)", `macos-26`) and `tests-macos-27.yaml` ("Tests (macOS 27)", `xcode-27`; both pass `browsers: chrome,firefox,safari` since `feat/safari-suite`, 2026-10-22 — a red Safari `Test` step skips the `Conformance` step of every browser, accepted until Safari is stable: GitHub has no `macos-27` label yet, macOS 27.0.1 / Safari 27.0.1 come only with the Xcode 27 image in public preview — move to `macos-27` once it exists; one file per macOS since `tests.yaml` names its log artifact `test-logs-<runner.os>`, the same for both)** — split from `tests-macos.yaml` (`macos-latest`) on 2026-10-21, branch `ci/macos-26-27`; first runs in MACOS-26-27 (`mem:measurements/ci-runners`). `pnpm build`, `pnpm test`, `pnpm test:conformance`, and on failure the `.work/` logs as an artifact `test-logs-<OS>` (14 days). The callers are **`workflow_dispatch` only**: dispatchable once the files are on `main` (`gh workflow run tests-windows.yaml --ref <branch>`); a temporary `push` trigger on the branch ran them before that. Per-platform triggers are the user's to choose later; putting them in the release is the next step after they ran well (user, 2026-10-14). Durations and counts: LIB-WIN-MAC, `mem:measurements/test-browsers`.
- **A timed-out test gets one retry on a slower platform, never at Linux speed (2026-11-04, `test/retry-timeouts-on-slow-runners`, user).** `tests/vitest.config.ts` sets every browser project's `retry` to `timeoutRetry(TIME_SCALE)` (`scripts/processes.ts`): `0` at `BSQ_TIME_SCALE` 1 (Linux CI, the release, local runs), `{ count: 1, condition: /^(Test|Hook) timed out in / }` above it (macOS 2, Windows 4) — a wrong result is never retried, and a file that fails to load is not a test, so not retried either. Why: a starved runner silences a worker past any bound (`mem:follow-ups/macos-ci-instability`), and the rule is no red on a library that works without fewer browsers or OS (user, 2026-11-04); at scale 1 a timeout stays red at once, as ABANDON-WEDGE did. **A test that passed on its retry is reported apart, never as a plain pass:** `Passed on retry (n tests) — it ran out of time first: look at it` with its cells after the merged report (`scripts/skip-notes.ts` `formatRetried`), a `retried` event from `scripts/progress-reporter.ts`, a `### Passed on retry (n)` section and `n retried` in the progress check run's title (`scripts/ci-progress.ts`), `RETRIED …` lines in `ci-watch.ts`. Verified 2026-11-04 with a throwaway test timing out once: retried and listed at scale 2, red at scale 1, its event marked. Not handled: a retry runs while the first attempt's leftovers may still run (Vitest cannot cancel a timed-out test).
- **The live progress check run (2026-11-03, `feat/ci-live-progress`, design `docs/superpowers/specs/2026-11-03-ci-live-progress-design.md`).** A job's log cannot be read through the API until the job ends; so on CI every planner (`test-plan.ts`, hence `pnpm test` and each matrix pair; `test-parallel.ts`, hence the conformance) publishes a check run `progress · <workflow> · <BSQ_PROGRESS_LABEL or job> · <test|conformance>`, `external_id` `<run id>/<attempt>`, and prints `Live progress: <url>` in the job log. Its summary: a header, `### Failed tests (n)` (each failed test as it fails, from `scripts/progress-reporter.ts`, which every Vitest process the planners start appends to `events/<job>.ndjson`; file and hook errors too), then `### Jobs` (the `[n/N]` lines). `scripts/ci-progress.ts` is the only writer, PATCHes only when something changed, at most every 10 s (the token's 1 000 requests/hour are shared by the repository), stops with one warning on any refusal or timeout and never changes the planner's exit; its conclusion is the planner's (`success`/`failure`). **No annotations**: GitHub files such check runs under any workflow's suite of the commit (CHECK-PROGRESS, `mem:measurements/ci-runners`), so they would show on another run's page; a foreign `failure` check run does not change that run's conclusion. **Permissions:** the repository's default token is read-only and a called workflow cannot exceed its caller, so `checks: write` is granted by `tests.yaml`'s and `matrix.yaml`'s jobs AND by every caller (`ci.yaml` `linux`, the four `tests-<os>.yaml`, the release's `verify` and `matrix`). **Closing step:** `Close progress`, `if: always()`, closes with `job.status` any check run the job recorded in `$RUNNER_TEMP/bsq-progress-ids` and left open (a cancel, a timeout, `fail-fast`, a planner killed by `bounded.ts`). **Following a run:** `node scripts/ci-watch.ts <run-id>` (or `--sha <sha>`) polls through `gh api` every 15 s, prints each new failure and `[n/N]` line once, then each run's conclusion; it stops 4 polls after the runs end even if a check run stayed open, and after 4 failed polls in a row (exit 2). Off CI or without a token nothing is published.
- `.github/workflows/ci.yaml` — on push to `main` and every PR (and `workflow_call` from the release, when the push of `main` left no passing run to reuse); WebdriverIO's browsers cached by the hash of `scripts/browsers.ts`; `concurrency` cancels superseded runs. **Every job that drives a browser (`tests.yaml`'s, the release's `consumer-smoke`, `matrix.yaml`'s `cells`, `pages.yaml`'s bench check) runs two steps after the cache (2026-10-11):** `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0` — the runner has it at 1, and Chrome for Testing, having no AppArmor profile, then exits at launch ("Chrome instance exited"); lifting it keeps the sandbox, `--no-sandbox` would drop it — and `node scripts/browsers.ts install`, so the browsers and drivers download once, before `test-parallel` starts jobs that would race on a cold cache (chromedriver spawned before it was executable, `EACCES`). First green run on the WebdriverIO suite: PR #7, run 38182346151.

- `.github/workflows/release-and-publish.yaml` — on `v*` tags. **Since 2026-11-03 (`ci/matrix-os`) `prior` looks for ONE run, `ci.yaml`'s push run on the tagged commit, which holds the matrix; the separate `matrix` job is gone and `verify` (calling `ci.yaml`) runs the matrix too when that run is not reusable. A tag on a commit of `main` pushed before that merge would reuse a CI run without the matrix.** What follows describes the two-run version of 2026-10-13. **Its `prior` job (2026-10-13) reuses the runs of the push of `main`**: for `ci.yaml` and `matrix.yaml` it finds the latest `push` run on the tagged commit (`gh run list --commit <sha> --event push`), waits for it (`gh run watch --exit-status`, both waits under one `timeout` deadline of 50 of the job's 60 minutes, so running out means `rerun` rather than a killed job that `untag` would answer by deleting a good tag), and outputs `success` or `rerun`; `verify` (calls `ci.yaml`) and `matrix` (calls `matrix.yaml`) run only on `rerun` — none, cancelled by a later push of `main`, failed. `consumer-smoke` always runs. `release` and `untag` need all four; `release` carries `if: ${{ !cancelled() && !failure() }}` because a skipped need would skip it. Then `pages` with `needs: release`. Pushing `main` and the tag together or apart gives the same result. Checked by hand before writing it: `gh run watch` on a completed run answers at once (0 passed, 1 failed). The wiring itself is proven only by the next release.
- **`.github/workflows/matrix.yaml` — a reusable module since 2026-11-03 (`ci/matrix-os`, design `docs/superpowers/specs/2026-11-03-matrix-os-design.md`), `workflow_call` only, as `tests.yaml`.** Inputs: `runs-on` (required), `browsers` (default `chrome,firefox`), `time-scale` (default `'1'`, `BSQ_TIME_SCALE` in both jobs), `timeout-minutes` (pair jobs, default 25), `plan-timeout-minutes` (default 15), `fail-fast` (default `false`; the callers that gate pass `true`). `plan` runs on the target runner with the target browsers (`--browser` each, the setup action enabling `safaridriver` when Safari is named) and outputs the pairs with a non-empty cell; `cells` runs one job per pair, `test-matrix.ts --pair <pair>` with `--engine <b> --engine isolated-<b>` per browser. **Callers:** `ci.yaml`'s `matrix` job (`ubuntu-latest`, `fail-fast: true`, no condition: every push of `main`, every pull request, the release through `ci.yaml` — the matrix shows inside the `CI` run since then); `matrix-ubuntu.yaml`, `matrix-windows.yaml` (`time-scale '4'`, 150/60 min), `matrix-macos-26.yaml` and `matrix-macos-27.yaml` (`xcode-27`; `chrome,firefox,safari`, `time-scale '2'`, 120/30 min), all `workflow_dispatch` only, each with its own concurrency group, going to the end (no fail-fast). The OS timeouts follow `resolveConcurrency`: the planner runs cores-less-one cells at once (2 on the macOS runners' 3 vCPU, 3 on Windows' 4), each bounded at 900 s × scale. First runs: MATRIX-OS, `mem:measurements/ci-runners`. Before 2026-11-03 it had its own triggers (every push of `main`, dispatch, the release's call) beside `ci.yaml`; first green on GitHub 2026-10-13 (run 38387953580, 23/23 in ~8 min).
- **A dead test fails CI in two places:** `matrix.yaml`'s `plan` (all-pairs, always fatal) and `ci.yaml`'s `linux` (`pnpm test` is complement mode; `scripts/plan-report.ts`'s `deadIsFatal` makes a full complement run fatal under `CI=true`, a warning locally — checked 2026-10-13 with a throwaway dead test: exit 1 under `CI=true`, 0 without). A dead standalone test is caught only by `linux` (all-pairs leaves standalone tests out). A normal run that a dead test fails says so on its last line.
- `.github/workflows/pages.yaml` — **the site is a pure function of two tags** since 2026-09-03: `/` is the latest release tag, `/preview/` is the `preview` tag when one exists. **The ref that triggered a run is never built and never consulted**, so every trigger produces the same site and re-running anything is idempotent. Want a preview: `git tag -f preview && git push -f origin preview`. Want it gone: delete the tag.

  Triggers: `workflow_call` (from release-and-publish), push of `preview`, and `delete`. **`push` does NOT fire for a deleted ref** — `delete` is the event for that, it carries no ref filter, hence a job-level guard.

  **The bench check (2026-10-13).** Before `upload-pages-artifact`, `scripts/bench/check.ts chrome --all --dir <half>` runs from the workspace checkout on the half a run builds anew: the root (`_site`) when a release calls it (`github.ref` is its `v*` tag), `/preview/` (`_site/preview`) on a push of `preview`, nothing on `delete`. Each half is built from its own tag, page HTML included, so the root a release checked stays checked. A red page stops the deployment, not the npm publication, which comes before. **Proven on 2026-10-13** by the push of `preview` on `e5855bb`: run 38448872714, `--dir "_site/preview"` checked, then deployed, green in ~3 min.

  **The root resolves `/releases/latest` FIRST and falls back to the list, and that order is load-bearing.** `latest` is the release GitHub designates and the one npm's `latest` dist-tag follows — which is what the page's badge claims the root to be. The list alone would put the root on the newest rc once a stable version exists, while `npm i browser-sqlite` still served the stable one, and the badge would be a lie. But **every release cut so far is a PRERELEASE and `latest` excludes those**, so it answers 404 today: `gh release view` and `GET /releases/latest` both said "release not found", which is how the first preview run failed on 2026-09-03. Hence the fallback to `GET /releases?per_page=20`, newest first, drafts filtered out. The fallback stops being the live path the day a stable version ships.

  **`gh api` writes the response BODY to stdout when it fails**, and `--jq` does not filter it. So `VAR=$(gh api … || true)` captures `{"message":"Not Found",…}` as if it were data — it passed every emptiness test and died three steps later in `actions/checkout` with `fatal: invalid refspec '+refs/heads/{"message":"Not Found"…'`. **Gate on the exit status** — `if VAR=$(gh api …); then` — and shape-check anything that reaches a checkout.

  What bites, all of it silent:
  - **Order.** `assemble.ts` opens with `rmSync(target, …)`, so the root must be assembled BEFORE the preview that sits inside it. The reverse deletes the preview.
  - **The root's ASSEMBLER is copied in from the triggering checkout; only its content comes from the release tag.** Otherwise the step runs the released tag's own assembler, frozen at whatever shipped, which predates the flags and falls back to the environment — and the environment names the TRIGGER. On 2026-09-03 that made the root label itself `preview`; harmless only because the badge does not print the ref when `IS_RELEASE` is true, and a lie the moment a `delete` run sets REF_TYPE to `branch` and the real release shows "development build". The copy degrades to a no-op once a release ships a script that takes the flags.
  - **The preview step runs the preview tree's OWN assembler, and its name depends on the tag**: `assemble.mjs` before 2026-10-03, `assemble.ts` since. The step takes whichever exists; hard-coding one name fails on a preview tag from the other side of the rename.
  - **The build label is passed to `assemble.ts` as an ARGUMENT — `--ref` and `--release` — never through the environment.** Actions reposes the `GITHUB_*` variables for every step and IGNORES a step-level `env:` that tries to override them, so a run building a ref other than its trigger cannot describe itself that way. Overriding them was tried and shipped on 2026-09-03: both halves came out labelled with the triggering tag and BOTH claimed to be the published package, `/preview/` included. The preview passes no `--release`, which is the point — `preview` IS a tag, and without an explicit label the script takes any tag for a release tag.
  - **A `delete` run executes from the DEFAULT BRANCH**, so its deployment presents `refs/heads/main`. An environment restricted to tags refuses it, and a deleted tag then leaves its preview up until the next release. `main` must stay allowed for deletion to work.
  - **A run that publishes nothing could cancel one that does, and did.** `cancel-in-progress` on a shared group, `concurrency` evaluated before any job runs, and `delete` with no ref filter: deleting a merged branch on 2026-09-04 killed the preview deploy pushed two seconds earlier, then skipped itself, leaving the site on the previous build with nothing to say so. Fixed by repeating the job's guard in the group expression, so a skipping run gets `pages-noop-<run_id>` and contends with nobody. **The two conditions must stay identical; `concurrency` cannot read `env`.** The expression was verified valid on GitHub; the cancellation itself was never staged.

  **Which workflow FILE runs differs by trigger**, and it bites once: a `push` runs the file as it exists at the pushed commit, so tagging a commit that predates a change to this file fires nothing. `delete` reads the default branch; `workflow_call` runs at the caller's ref. There is no `workflow_dispatch` — removed on the user's instruction, 2026-09-03. **Re-pushing the tag UNCHANGED does nothing** — git answers `Everything up-to-date` and emits no event, so no run starts (believed otherwise until 2026-09-04). To republish without moving it: `git push origin --delete preview && git push origin preview`, which briefly takes the preview down.

  **The `github-pages` environment allows `main`, the `v*` tags and the `preview` tag** (user, 2026-09-03). `main` is there for one reason and it is not obvious: `delete` runs from the default branch, so without it a deleted `preview` tag could not take its preview down. `feat/*` was dropped — no branch deploys any more. Putting unmerged work on a real device through the `preview` tag is an exposure kept deliberately (user, 2026-08-26), which is what makes the page's "development build" banner and `buildRef()` in `scripts/bench/assemble.ts` load-bearing.
