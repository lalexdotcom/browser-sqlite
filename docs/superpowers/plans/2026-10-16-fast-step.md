# Fast step Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The worker steps statements through a library-side fast step that stays synchronous when wa-sqlite's call completed synchronously, instead of wa-sqlite's `async` `step()` wrapper.

**Architecture:** A new module `src/worker/step.ts` reproduces wa-sqlite's `retry()` and `check()` around the per-build `sqlite3_step` call, returning a number when nothing suspended and a promise otherwise. Both `sqlite.step()` call sites in `src/worker/worker.ts` use it. A unit test fingerprints the wa-sqlite code it reproduces, so a repin that changes it fails until the fast step is reviewed.

**Tech Stack:** TypeScript, wa-sqlite (vendored, pin `6238f532` + `patches/wa-sqlite@1.1.2.patch`), Vitest (unit project in Node, browser projects through WebdriverIO).

**Spec:** `docs/superpowers/specs/2026-10-16-fast-step-design.md` — read it before any task.

## Review Focus

- **`jspi` and a promise compared to `SQLITE_ROW`.** A long read on `jspi` returns every row, not one. Pinned by Task 2's long-read test.
- **`async` suspending mid-statement** (the library's `async` progress handler fires every `PROGRESS_OPS` = 100 000 operations). A long read returns every row and the next query on the same worker works. Pinned by Task 2's long-read test (it runs a second query afterwards).
- **A step that throws synchronously inside `run()`'s `try`** — `SQLITE_INTERRUPT` from the slot poll on an isolated `sync` build must still hit the `break`, and every other error must still be `stamped()`. Pinned by the existing `interrupt.test.ts` and `statement-errors.test.ts`, run in Task 2.
- **An error from a pragma at open** must still produce the same `open-error` (`statement-errors.test.ts` › "fails the open with WORKER_CRASHED carrying NOTADB when a pragma reads it"), run in Task 2.
- **`pendingOps` from `OPFSWriteAheadVFS`'s `wal_checkpoint`** resolve before the step's code is returned. Pinned by Task 1's unit tests and, in the browser, by a `PRAGMA wal_checkpoint` test on `OPFSWriteAheadVFS` (Task 2 finds one or adds it).

### Task 1: The fast step module

**Files:**
- Create: `src/worker/step.ts`
- Modify: `src/wa-sqlite.d.ts` (the `WASQLiteModule` type)
- Test: `tests/unit/lib/step.test.ts`

**Interfaces:**
- Consumes: `SQLiteBuild` from `src/const/builds`; `SQLiteError` from `wa-sqlite/src/sqlite-api.js`.
- Produces:
  ```ts
  export type Step = (stmt: number) => number | Promise<number>;
  export function createStep(module: WASQLiteModule, build: SQLiteBuild, db: number): Step;
  ```
  `WASQLiteModule` gains `_sqlite3_step: (stmt: number) => number | Promise<number>`, `retryOps: Promise<unknown>[]`, `pendingOps: Promise<unknown>[]`, and a `ccall` typed for its two uses: `('sqlite3_step', 'number', ['number'], [number]) => number | Promise<number>` and `('sqlite3_errmsg', 'string', ['number'], [number]) => string`.

- [ ] **Step 0: Keep `main`'s build for the measurements (Task 4)**

The branch holds only the spec so far, so its build is `main`'s.
Run: `pnpm build && rm -rf .scratchpad/fast-step/dist-main && mkdir -p .scratchpad/fast-step && cp -r dist .scratchpad/fast-step/dist-main`
Expected: `.scratchpad/fast-step/dist-main/worker/worker.js` exists.

- [ ] **Step 1: Write the failing tests** in `tests/unit/lib/step.test.ts`, against a fake module built per test (a `_sqlite3_step` and a `ccall` driven by a script of return values, `retryOps`/`pendingOps` arrays, `ccall('sqlite3_errmsg', …)` returning `'fake message'`). Constants: `ROW = 100`, `DONE = 101`, `OK = 0`, `BUSY = 5`, `ERROR = 1`. One literal `it` per case:

  - `returns a number, synchronously, when the call returned a number and nothing is queued` — `sync`; `_sqlite3_step` → 100; `step(7)` is `100` (`typeof` `'number'`), `_sqlite3_step` called once with `7`. Same for 101.
  - `throws SQLiteError synchronously on any other code, with sqlite3_errmsg's text` — `sync`; → 19; `expect(() => step(7)).toThrow(SQLiteError)`, `code` 19, `message` `'fake message'`, `ccall` called with `('sqlite3_errmsg', 'string', ['number'], [db])`.
  - `looks at what came back, not at the build` — `sync`; `_sqlite3_step` → `Promise.resolve(100)`; `step(7)` is a promise resolving to 100.
  - `waits for retryOps queued before the call, then empties them` — `sync`; `retryOps` holds a deferred; `step(7)` is a promise; `_sqlite3_step` not called until the deferred resolves; then called once; resolves 100; `module.retryOps` is `[]` (a new array is fine).
  - `retries once when the call returns a non-OK code with retryOps queued` — `sync`; first call → 5 and pushes a resolved op into `module.retryOps`; second → 100; resolves 100, two calls.
  - `retries at most once` — both calls → 5, each pushing an op; rejects `SQLiteError` code 5; exactly two calls.
  - `does not retry SQLITE_OK even with retryOps queued` — call → 0 and pushes an op; rejects/throws `SQLiteError` code 0 (wa-sqlite's `check` refuses 0 for `step`); one call.
  - `waits for pendingOps after the call, then empties them` — call → 101 and pushes a deferred into `pendingOps`; result is a promise that stays pending until the deferred resolves; resolves 101; `module.pendingOps` is `[]`.
  - `turns a rejected pendingOp into its code` — pending op rejects `{ code: 10 }`; rejects `SQLiteError` code 10; `console.error` called with `'Error in pendingOps:'` and the error (spy, restored); `pendingOps` is `[]`. Without `code`: code 1.
  - `reads retryOps and pendingOps from the module at every call` — the fake replaces `module.retryOps` with a new array during a call (as wa-sqlite does); the queued op is still awaited.
  - `async: calls ccall without the async option` — `async`; `ccall('sqlite3_step', 'number', ['number'], [7])` → 100, `_sqlite3_step` never called, result `100` synchronously; when `ccall` returns `Promise.resolve(101)`, the result resolves 101. Assert the `ccall` call has exactly four arguments.
  - `jspi: awaits the promising export` — `jspi`; `_sqlite3_step` → `Promise.resolve(100)`; resolves 100 (not a truncated loop: the value is the resolved code).

Run: `pnpm exec vitest run --config tests/vitest.config.ts --configLoader runner --project unit tests/unit/lib/step.test.ts`
Expected: FAIL, `createStep` not exported / module not found.

- [ ] **Step 3: Implement `createStep(module, build, db): Step` in `src/worker/step.ts`, and the `WASQLiteModule` additions**

The semantics are the spec's "What the fast step reproduces" and "Anti-goals", exactly: the call is `module._sqlite3_step` on `sync` and `jspi`, `module.ccall('sqlite3_step', 'number', ['number'], [stmt])` (no fifth argument) on `async`; the fast path is "no `retryOps` before, a number back, no `retryOps`/`pendingOps` after → `check`"; anything else continues as `retry()` would from the call already made, never calling `sqlite.step`. `check` allows only `SQLITE_ROW` and `SQLITE_DONE`. A short header comment says what the module reproduces and that `tests/unit/lib/wa-sqlite-pin.test.ts` guards it.

Same command. Expected: PASS, all cases. Then `pnpm check` and `pnpm exec tsc --noEmit`, both clean.
