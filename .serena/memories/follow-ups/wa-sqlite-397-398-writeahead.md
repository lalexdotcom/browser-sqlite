# Follow-up — wa-sqlite issues #397 and #398: two `OPFSWriteAheadVFS` defects reported upstream (seen 2026-11-19)

**Status: OPEN** — both are ISSUES, not pull requests (`mem:state` called them PRs until 2026-11-19); opened by cdargel, open, no fix proposed upstream as of 2026-11-19. Nothing done here yet. Part of `mem:follow-ups`.

- **#397 — "WriteAhead: a failed write in commit() leaves `#txInProgress` set".** A write that fails inside `commit()` (a quota failure at commit reaches it) leaves the VFS believing a transaction is still in progress. Effect on the library not measured.
- **#398 — "WriteAhead: a passive checkpoint after an interrupted non-passive checkpoint can write older pages over newer ones".** A data-integrity report on a VFS the library recommends; the more serious of the two.
- **Why it matters here:** `OPFSWriteAheadVFS` is one of the recommended VFS (`RECOMMENDED_VFS`), and `patches/` carried our checkpoint rework (#361, merged upstream) on that same code.
- **Read 2026-11-19 (issues and pinned code `205eed58`, not run):** both issues are by cdargel (2026-11-14), each with a suggested fix and a repro on a model harness; #398's only comment is rhashimoto asking which version (cdargel cited a non-existent "1.7.0"), unanswered. **#397 reachable through the library:** `OPFSWriteAheadVFS` calls `writeAhead.commit()` on `SQLITE_FCNTL_SYNC`; `#commitTx` leaves `#txInProgress` set whether the 32-byte commit frame is short or the OPFS `write` throws (`QuotaExceededError` on a full origin); the VFS returns `SQLITE_IOERR`, which the library hands to the caller and keeps the worker (no special handling of IOERR in `src/`), so the next write on that worker joins the failed transaction. Needs the quota to run out exactly at the commit frame (page frames are written before it): narrow, unmeasured. **#398 reachable only after a consumer's non-passive checkpoint:** the auto-checkpoint is always passive; `wal_checkpoint(FULL|RESTART|TRUNCATE)` comes only from the consumer (`run()` or the `pragmas` option, `src/client.ts`). The writer must die between the database flush and `#truncateInactiveFile()` — a span that includes `#waitForTxIdLocks` (every reader catching up), so not tiny: `close({ immediate: true })`, a drain timeout or `handleDeath` during it; a later passive checkpoint by a new writer then writes older pages over newer ones. Unmeasured.
- **#397 fixed on the fork, 2026-11-23** (branch `opfswriteahead-commit-failure`, worktree `.work/wa-sqlite-wa-commit`, commit `e226501f` on upstream `205eed58`, not pushed): `commit()` calls `#abortTx()` when it fails with `#txInProgress` still set. Test `test/vfs_commit_failure.js` (+ worker wrapping `FileSystemSyncAccessHandle.prototype.write`), 3 cases × 3 builds, all red on `master` (18 failures), green with the fix; whole suite Chrome 16/16 files, 8 238 passed. Measured beyond the issue: a failed connection that READS after the failure keeps the refused page in its pager cache (page 1's change counter, cached in the WriteAhead entry, equals the other writer's), so another connection's commit in between is lost (`[1, 2, 3]` for `[1, 3, 10]`, `integrity_check` ok); without that read the stale entries fall on the other writer's frames and the result is right by chance. PR body draft `.scratchpad/pr-writeahead-commit-failure.md`.
