# Follow-up — carry wa-sqlite PR #393: `OPFSCoopSyncVFS` misses a hot journal left by a terminated connection (issue #392, 2026-11-06)

**Status: OPEN** — to test, then carry in `patches/`; the PR is not ours (justshrey), open, not reviewed as of 2026-11-06.

Part of `mem:follow-ups`.

**The defect ([#392](https://github.com/rhashimoto/wa-sqlite/issues/392), opened 2026-11-05).** `jAccess` answers only from `accessiblePaths`, filled at the first open from the files' sizes and afterwards changed only by the connection's own `xOpen`/`xDelete`. `#requestAccessHandle` takes the handles back from another connection without looking at what it left. A connection already open therefore never sees the `-journal` of a connection terminated inside a write transaction: SQLite skips its hot-journal check and reads the half-applied transaction (`database disk image is malformed`, or uncommitted values with `integrity_check` = `ok`). If that survivor writes next, its commit truncates the journal and the database cannot be recovered. A connection opened *after* the termination rolls back correctly. `jOpen` would also refuse the journal (`File … not found`, no `SQLITE_OPEN_CREATE`) even if `xAccess` answered right. Needs a transaction larger than the page cache (2 MB default; the library sets no `cache_size`), so SQLite spills pages to the file before commit.

**The fix ([#393](https://github.com/rhashimoto/wa-sqlite/pull/393), opened 2026-11-05).** Once `#requestAccessHandle` holds the three handles, it adds each file of `DB_RELATED_FILE_SUFFIXES` with `getSize() > 0` to `accessiblePaths`; the size check of `#createPersistentFile` is removed (the first open goes through `#requestAccessHandle` too). Placement is right: `jLock` returns `SQLITE_BUSY` until the handles are held, and SQLite calls `xAccess` only after the lock succeeds. Cost: three synchronous `getSize()` per handover, not per transaction. Add-only: a stale "exists" is harmless (SQLite reads the header and ignores a journal that is not hot); a symmetric refresh would be more exact, a nit. Test `test/vfs_hot_journal.js` (3 builds): red on master for an already-open survivor, green with the change; relies on #381's hand-over retry (merged). Read from source on 2026-11-06, not run yet.

**Library exposure (read from `mem:vfs` and `mem:architecture`, not measured).** Within one client the library avoids it: `OPFSCoopSyncVFS` has `maxPoolSize: 1`, and a worker replacing a dead one opens after the death. **Across tabs, or two clients on one database, it does not:** the origin-wide write lock serializes writes, not the other tab's already-open connection; a tab closed mid-transaction (no `close()`, Web Locks released at once) leaves exactly #392's scenario. Same for `handleDeath`, `onPoisoned` or a drain timeout terminating a worker of one client while another client is open.
