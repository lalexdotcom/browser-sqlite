| 2026-09-14 | `fix/pool-environment-cap` | **A pool the environment caps is capped, not lost — and a pool that buys nothing runs one worker.** Every Firefox run of a probe logged `worker 1 lost`: off Chromium, `OPFSWriteAheadVFS` keeps its file exclusively for a connection's life, so every worker but one failed to open — and the 2026-08-27 commit that had "refuted" exactly that claim was wrong, because conformance never counted live workers. Surplus workers now probe `readwrite-unsafe` inside the worker (`'mode' in FileSystemSyncAccessHandle.prototype`, measured on all three engines) before loading anything and decline; the client retires them without `onWorkerLost`, exposes `db.poolSize`, warns once only on an explicit `poolSize`, and an open failure carries the VFS's own error. A measurement (POOL-SIZE) then showed that a pool buys nothing on a rotated handle: `OPFSAdaptiveVFS` runs one worker without `readwrite-unsafe`, `OPFSCoopSyncVFS` one everywhere (breaking: `poolSize` > 1 throws), and fifteen pool-mechanics tests moved to `OPFSAnyContextVFS`. Found on the way and fixed: `deleteDatabase` left `-wa0`/`-wa1` behind; `close()` waited `drainTimeout` for a worker that died while closing; a retry-round decline was announced lost. Found and left: CoopSync writes can take the transfer BUSY between clients; the barrier test does not guard the barrier. Spec with amendments §9-§10, a plan of thirteen tasks by subagents, two final reviews, three fix waves. Merge `121b0f6`. |
| 2026-09-14 | `fix/idb-long-read` | **`IDBBatchAtomicVFS` serves reads during a long statement, signal or not.** It began as "the bench says IDB serves on Firefox, the docs say it waits". Split by commit, the corpus flipped exactly at `f4b3fd7`: the bench row passed its signal to the long query, and since then an abortable statement yields — which lets IDB's per-statement readwrite IndexedDB transaction commit, while an unsignalled long read still held every other connection's read for its whole duration. A `yieldsDuringStatements` capability makes every IDB statement yield, measured free on three engines; the bench row now asks what a plain read meets. Verifying it on Safari uncovered what the bench's `null` there really was: wa-sqlite's `async` (Asyncify) build slows down run after run on Safari, and stays slow — not IndexedDB, not the library, not Chromium or Firefox — while `jspi` escapes it on Safari 27. Defaulting to the first supported build is scheduled for rc.6. Found and left: a load-sensitive timeout race on Firefox; wa-sqlite reading `FileSystemSyncAccessHandle` at module load. Measured through ten console probes the user pasted, and a bench served from the container on `localhost:8099`. |
| 2026-09-15 | `fix/coopsync-handle-release` | **An `OPFSCoopSyncVFS` write no longer fails with `BUSY` when another client uses the same database.** The backlog entry said "the handle-transfer BUSY"; a lock trace said otherwise: SQLite locks, unlocks and locks again inside one `sqlite3_step` when it re-prepares a statement whose schema changed, the VFS gave its single handle away at that inner unlock, and wa-sqlite's `retry()` — two tries — returned the relock's `SQLITE_BUSY`. Two clients opened together failed an early write; a write after another tab's `CREATE TABLE` failed 17-18 times in 20 on Firefox; every other VFS, never. Fixed in a wa-sqlite patch that hands the handle over from a task after the call — the first version, a microtask, was reasoned safe and still failed on `jspi`, where every VFS call runs microtasks — plus `#initialize` ignoring a temporary directory another instance deleted first. wa-sqlite is now pinned by SHA to upstream `07ad48c` (user), which carries the AnyContext fix, so the patch holds the CoopSync change only; upstream as rhashimoto/wa-sqlite#347, with tests in its own suite that fail on its master, CI green. Found and left: `OPFSWriteAheadVFS` refuses a second client off Chromium, and the multi-client and cross-tab suites run on one VFS — the next session. One commit plus merge; no spec, designed in chat. |
| 2026-09-15 | `feat/statement-errors` | **A failed statement says why.** Every statement SQLite refused reached the consumer as a plain `Error`: the worker sent the code, and the client kept it only for BUSY. It is now `STATEMENT_FAILED`, with `sqliteCode` (primary, typed `SQLiteResultCode`) and `sqliteExtendedCode` (the subtype, only when SQLite reports one, read in the worker where the statement fails, before a reset, a finalize or the savepoint path's ROLLBACK can overwrite it). `WORKER_CRASHED` at open and delete carries `sqliteCode`, taken only from wa-sqlite's own `SQLiteError`. `SQLITE_CODES`/`SQLITE_EXTENDED_CODES` are exported. The user amended the design three times while it was built: two tables rather than one (D8), no extended code without a subtype (D9), a strict primary type (D10, measured on the language service first). The final review found the worker publishing a DOMException's legacy `code` as SQLite's, and a stamp a fix round had left without a falsifier. Breaking. Spec with D8-D10, a plan of four tasks — three by subagents, the docs with the user — one final fix wave. Merge `54c4492`. |
