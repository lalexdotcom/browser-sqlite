# Follow-up — a cleanup's `deleteDatabase` past its 30 s on Windows Firefox, `IDBBatchAtomicVFS/jspi` (2026-11-14)

**Status: OPEN** — instrumented and the cleanup's bound scaled on `fix/delete-timeout-stage` (2026-11-14); the cause is unmeasured: read the step the next sighting names.

Part of `mem:follow-ups`.

- **Seen:** Windows matrix of `main` `1aa04a0a` (run 43613231041, job 132503184146), cell `firefox · IDBBatchAtomicVFS/jspi`, `close.test.ts` › "close() > waits for the worker to close the database before terminating it" — its own assertions passed; the `cleanUp` registered by `createTestClient` (`tests/browser/helpers/index.ts`) failed: `WORKER_TIMEOUT: deleting bsq-test-… did not complete within 30000 ms: the worker deleting it did not answer.` The test took 74.9 s (its file's others 0.6-25.6 s). The cleanup passed no `timeout`, so the library's default 30 s applied, which `BSQ_TIME_SCALE=4` does not stretch. Same matrix: macOS 27 lost two cells to safaridriver (`mem:follow-ups/macos-ci-instability`), unrelated.
- **Hypothesis (not verified):** `mem:follow-ups/idb-unknown-error-delete`'s mechanism — Firefox on a Windows runner holds an IndexedDB database busy while a connection closes; the next open busy-waits 10 s and fails `UnknownError`, and `createVfsInstance` retries. **The "~30 s worst case, which is `DEFAULT_DELETE_TIMEOUT`" first written here was wrong (re-read 2026-11-16):** `busyDeadline` is the first failure + `BUSY_RETRY_BUDGET_MS`, and a retry gives up only once `now >= deadline`. Against a file that stays busy every attempt lasts Firefox's 10 s, so: attempt 1 fails at ~10 s, attempt 2 (10.1 s) succeeds if the close ends before ~20 s, else fails at ~20.1 s, past the deadline, and the error surfaces. **Worst case ≈ 20 s plus the worker's boot**, under the 30 s default; 30 s would need attempts failing faster than Firefox's 10 s, which this mechanism does not do. For the 2026-11-14 sighting to be this mechanism, a close past ~20 s or a boot of ~10 s was needed — possible on a Windows runner, so the hypothesis is weaker than first stated.
- **Decided (user, 2026-11-16): no library change before the release, no duration tuned.** Both 10 s budgets rest on one measurement each (`src/worker/create-vfs.ts`); other values would be as arbitrary, and nothing shows them past the 30 s default. Wait for the stage the next sighting names. **Deferred, not for the release:** bound the retry by the caller's remaining deadline — the delete message carries the remaining duration (not an absolute time: the page's and the worker's `performance.now()` have different origins), `createVfsInstance` does not start an attempt that cannot end before it (a Firefox attempt lasts up to 10 s) and throws the last error instead; the same for a client's open under `openTimeout`. It succeeds no more deletions: it makes a failure under a short caller `timeout` name its cause instead of a mute `WORKER_TIMEOUT`.
