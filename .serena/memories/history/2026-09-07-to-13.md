| 2026-09-09 | `fix/abandoned-generator` | **A `chunk()`/`stream()` generator dropped without `break`, `return()` or exhaustion no longer strands its worker for the life of the page.** It never replayed its three `finally` blocks, so the worker stayed leased and parked between two `step()` calls with its read transaction open; two of them wedged a client at `poolSize` 2, silently. Repaired in two halves: a `FinalizationRegistry` net that is best effort and says so, and — the half everything is tested on — a `signal` or `timeout` that runs the same teardown **at the abort** instead of only rejecting the next pull. A transaction now closes the generators its callback left open, interrupting the transport first because a method call on an async generator queues behind an in-flight `next()`. New public code `GENERATOR_ABANDONED`, replacing a bare `Error`; `interrupt()`'s transport argument became required. **The branch produced three defects of the class it was repairing, and none was found by re-reading the plan**: a `Promise.race` that resolved ties among pre-settled inputs by array position and dropped 3900 of 4000 rows, bisected against `main`; a permanent pool wedge on Firefox, where evicting a worker stranded the rotated exclusive OPFS handle; and an `await gen.return()` parked behind an in-flight `next()` that held the origin's write lock indefinitely. Two were caught by whole-branch reviews, one by an implementer who refused to work around a red test. The closure was stopped by a one-in-eighteen flake that a systematic-debugging session turned into HANDLE-2 — pre-existing, unfixed, and the largest thing this branch uncovered without touching. 25 commits, seven tasks, two whole-branch reviews, five fix rounds; spec amendments A1-A5 record what implementation disproved. Merge `ddd8270`. |
| 2026-09-09 | `fix/close-write-lock` | **A transaction whose callback never returned blocked every write in the origin, in every tab, for ever — and `close()` reported success without releasing the lock.** Found while hunting HANDLE-2, which came apart instead: its stated cause is measured false (Firefox returns a killed worker's sync access handle in 1-6 ms) and its wedge does not reproduce, on `main` or at the pre-fix commit where 9/40 was recorded. Four changes: `close()` reclaims the write locks its own leases never gave back; a write that spends its `timeout` on that lock says whether this tab or another holds it, in three states because the lock may be free by the time it looks; `PoolWorker.terminate()` poisons its transport before stopping the thread, since it was the native `Worker` method and a request posted afterwards — a transaction's next statement, its unsignalled fallback `ROLLBACK` — waited for a reply that could never come; and the client's close signal joins the transaction's own, so closing abandons a running transaction instead of leaving its promise pending for the life of the page. **Bounding the holder was proposed and refused, with the reasoning kept**: a callback awaiting a slow producer and one stuck for ever are indistinguishable from outside. The `close()` asymmetry that remains is durability, not transactions — an ordinary write is drained because rejecting it would report failure for a row that landed. One commit plus merge; no spec, the design was settled in chat in four validated steps. Breaking: a transaction left unawaited now surfaces an unhandled rejection, which is how the defect was caught in this repository's own suite. |
| 2026-09-11 | `fix/tx-statement-timeout` | **A transaction ends once, and its handle knows it.** It began as a per-statement `timeout` inside `transaction()` that was silently ignored. Restoring it exposed that an interrupted write makes SQLite roll the whole transaction back unseen — later rows landed in autocommit while the transaction reported failure, the fallback `ROLLBACK` evicted the worker, and on a memory VFS the eviction wiped the database. Verifying one of the design's own claims then found a released defect: a `tx` handle outlived its transaction and rolled back, or joined, the next one on the same worker. The worker now reports `inTransaction`; a transaction records how it ended and its handle refuses everything with the new `TRANSACTION_CLOSED`; a write abandoned while it runs abandons its transaction; `tx.signal` aborts whenever `transaction()` rejects. After the whole-branch review the user reversed D4 (a pre-aborted write rejects alone) and widened `tx.signal` to every rejection; savepoints went to `mem:follow-ups`. One commit landed past the hook with a failing `tsc` and was caught at the next commit. Spec and plan dated 2026-09-10, six tasks by subagents, one whole-branch review, one fix wave. Merge `eeabe06`, 18 commits. |
| 2026-09-12 | `fix/tx-savepoint` | **A caught write abort leaves the transaction whole.** A statement abandoned by its own `signal`/`timeout` inside `transaction()` now has no effect, and a callback that catches it goes on — SQLite's statement-level model, chosen by the user over PostgreSQL's. SQLite closes every savepoint when it interrupts a write, so the write is not cut: the worker runs it inside `__bsq_sp`, opened in the write's own message and concluded by the transaction's next one (approach B, the user's choice over the recommended A after both were measured — 0.016-0.019 ms per opted-in write on Chromium, 0.085 ms on Firefox); every entry point waits for an abandoned write; `bulkWrite`/`output` batches are savepointed one by one; transaction-control statements are never wrapped. The plan missed one test pinning the superseded rule; the final review found the spec's "a failed conclusion kills the transaction" unbuilt — an abandoned `…; RELEASE u` could commit a rejected write — and two R2 tests green under their own mutation, all fixed in one wave. Spec and plan dated 2026-09-11, eight tasks by subagents, one final fix wave. Merge `65a40d3`, 16 commits. |
